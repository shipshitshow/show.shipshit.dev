# Source-led show preparation

Create a show the hosts can navigate while speaking in their own words. Keep the existing skill name for compatibility. The board has one exception to "no scripts": the first sentence on air is prepared and approved. Everything after it stays natural.

## Channel context

Use the user's channel profile and actual source asset. For Ship Sh*t Show, read [the bundled profile](references/channel-profile.md); viewers using another channel should provide their audience, voice, formats, links and visual references. A profile is context, not permission to publish, upload footage, buy generation or contact a partner.

## Prepare

Start from the viewer question and the hosts' actual experience. Review the latest relevant transcript if available. Select a small set of source clusters; locate the useful tweet, passage, timestamp or result before the show. Prefer primary evidence alongside X discussion. Mark unverified claims and do not fill gaps with invented experiences or invented host opinions.

### One title, one promise

The title makes one promise and the show keeps it. At most three segments plus a close. A topic that does not help answer the title moves to an after-show block on the board, to the next episode, or is dropped. Order the segments by the decision the viewer needs to make, with the main proof early; use release chronology only where it explains that decision.

### The first sentence

If the stream opens with a countdown or holding card, that is deliberate and not part of the show. The first spoken sentence after it is the episode's promise, said to the lens: a claim plus the stake for the viewer, under 15 seconds. Prepare two or three options with [the opening guide](references/opening-and-hooks.md), and have the hosts approve one with the board. Stream and audio checks happen before going live; greetings and catch-up go to an after-show block of five minutes at most, after the close. By about 45 seconds the first useful point has started.

### Stance check

Ask each host for a one-line verdict per segment before the show. Record only what a host says; never write a host's view for them. Mark each segment `Split` where the verdicts differ: that is the segment worth the time. Where they agree, one host takes the sceptical customer's side and asks the questions that customer would ask. If a host has no view yet, mark the segment `Open` and give it a question, or cut it. Nothing is faked: plan the question, not the disagreement.

### Story first, source second

Each segment opens with what happened to a host: one firsthand story and one number per host, labelled as the host's own. Mark `No firsthand: ask` where one is missing and either cut the segment or run it as an open question. The source shrinks to one line both hosts have already read, with the link. If neither host read it before the show, it is not in the show.

### Pace and chat

Plan a one-sentence re-hook every 8 to 10 minutes: what is already answered and what the viewer still gets. Plan one chat question per segment; a planted one from the hosts' own notes is fine. For a live build or demo, plan what the hosts will say while it runs, or do the wait off air. Plan the close as one sentence per host on what they would do on Monday, and end the show there.

### Demo

If a demo is requested, verify quota/account, fixture, expected result and a short recovery path. Prepare an authorized recorded/local fallback when live usage is unreliable. Mark the slot unavailable if neither exists; do not promise it or purchase capacity silently.

### Output

Use [the source-board template](references/output-template.md) and [the segment playbook](references/segment-playbook.md). Return the first-sentence options, terse talking points (2–5 bullets of under 12 words per segment, no full sentences, no stage directions; budgets, exits, re-hooks and on-screen notes go under Producer notes), an `announcement_tweet` and navigable links. Do not return an opening monologue, quotes to perform, mandatory clip lines or a forced publishable build. An exit cue helps move on without scripting a conclusion the evidence does not support.

For an app topic file, preserve its frontmatter and use `## Sources — <segment>` with `###` subheadings. Confirm the target renderer's section rules; avoid nesting `##` inside a segment. Use a separate complete run-of-show note when the app stores one file per topic.

Attach [the on-air checklist](references/on-air-checklist.md) to the run sheet the hosts look at while live.

## Review

Run [the quality gate](references/content-quality-gate.md) before handing over the board. In short: does the first sentence stand alone, does the title's promise arrive in the first segment, do three segments or fewer carry it, is the stance of each host recorded or marked open, does every segment open on a story, can each host find the next source immediately, is the demo executable, are opinions and evidence distinguishable, and does the ending answer the viewer question or state what remains unknown?

After the show, record actual segment timing, time to the first claim, confusing transitions and demo outcomes. Compare retention for similar formats before attributing performance to an editorial change.
